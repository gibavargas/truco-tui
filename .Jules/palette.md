## 2025-03-11 - Playing Card Accessibility\n**Learning:** When rendering custom CSS-based playing cards that use repeated characters and decorative unicode symbols for the suit, screen readers will read out confusing, nonsensical strings like '4 ♦ ♦ 4 ♦'. To fix this, mark the entire card container with `role="img"` and an `aria-label` containing the readable label (e.g. '4 de Ouros'), while setting `aria-hidden="true"` on all the child elements containing the visual symbols and duplicating caption texts. \n**Action:** Use this `role="img"` with `aria-label` pattern anytime visual text/unicode combinations act purely as decorative graphical elements rather than meaningful flowing text.

## 2025-06-22 - Form Validation and Chat Input Accessibility
**Learning:** For compact inputs like the `chat` bar that do not have an explicitly visible `<label>`, relying purely on `placeholder` attributes is insufficient for screen readers. Furthermore, handling basic required fields via custom JS can be bypassed or fail cleanly. Using native HTML5 `required` along with `aria-label` bound directly to the placeholder's translation key provides a robust, zero-dependency validation pattern and ensures accessibility compliance. Note that fields that have meaningful default actions when left empty (like `relay_url` defaulting to the public relay) must *not* be marked required.
**Action:** Always map implicit fields (like search bars or chat inputs) with `aria-label` mirroring the placeholder, and prioritize native HTML5 form constraints (`required`, `type`, `pattern`) over custom JS validation for broad compatibility.

## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2024-08-09 - Timing Attack Vulnerability in Token Verification
**Vulnerability:** The invite token verification logic in `internal/netp2p/host.go` (`if joinMsg.Token != h.token`) was using standard string equality comparison (`!=`). This opens up the system to timing attacks because string comparison stops evaluating characters at the first mismatch, allowing an attacker to deduce a token by measuring the time each check takes.
**Learning:** Checking secure tokens or sensitive keys like invite tokens must always use constant-time operations to prevent side-channel timing attacks that leak secret data.
**Prevention:** Always use `crypto/subtle.ConstantTimeCompare` (by casting the strings to `[]byte` and checking if the result is `!= 1`) instead of standard equality operators (`==` or `!=`) when comparing sensitive strings.

## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2026-07-07 - Insecure TLS Fingerprint Verification
**Vulnerability:** The `tls_transport.go` package used `InsecureSkipVerify: true` with a custom `VerifyPeerCertificate` function to pin P2P self-signed certificates. The function did not verify certificate expiration (`NotBefore`/`NotAfter`) and used a standard string comparison (`!=`) instead of a constant-time comparison for the SHA-256 fingerprint hash.
**Learning:** While checking the fingerprint guarantees the certificate bytes match perfectly (and therefore expiration is also fixed since the bytes are hashed), omitting expiration checks allows an attacker to replay a genuinely expired pinned certificate if the user manually accepted an old invitation link. String comparison on cryptographic hashes (even public ones in some contexts) can introduce minor timing side channels.
**Prevention:** Always use `VerifyConnection` instead of `VerifyPeerCertificate` when skipping standard verification so `tls.ConnectionState` is available to explicitly enforce `NotBefore` and `NotAfter` checks on the pinned certs. Always use `crypto/subtle.ConstantTimeCompare` when comparing sensitive security hashes, even fingerprints.

## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2024-05-18 - Timing Side-Channel Vulnerability in Token Comparisons
**Vulnerability:** Security-sensitive tokens and credentials (`sess.AdminToken`, `req.PeerCredential`, etc.) were compared using standard string equality operators (`==` and `!=`).
**Learning:** Standard equality operators in Go (and many languages) short-circuit and return early as soon as the first mismatched byte is found. This creates a timing side-channel where the response time varies based on how many leading bytes match the expected secret. Attackers can statistically analyze these minute time differences to guess tokens or session IDs byte by byte.
**Prevention:** Always use `crypto/subtle.ConstantTimeCompare([]byte(a), []byte(b))` when comparing cryptographic secrets, session IDs, passwords, or authentication tokens to ensure comparison time depends only on the length of the slices and not their contents.

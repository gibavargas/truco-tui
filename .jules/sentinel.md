## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2026-09-27 - Timing Attacks in Token/Credential Verification\n**Vulnerability:** String equality operators (`==` or `!=`) were used to compare sensitive authentication tokens (`req.HostAdminToken`) and credentials (`req.PeerCredential`, `mem.Credential`) in `cmd/truco-relay/main.go`.\n**Learning:** Using standard string comparison operators on sensitive data makes the application vulnerable to timing attacks. An attacker can determine valid secrets byte-by-byte by observing the minuscule time differences it takes for the server to reject invalid strings, because string comparison aborts at the first non-matching byte.\n**Prevention:** Always use `crypto/subtle.ConstantTimeCompare` when comparing cryptographic tokens, passwords, secrets, or MACs. The length must be checked in constant time or by casting to byte slices where `ConstantTimeCompare` safely returns `0` if lengths differ.

## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2026-06-05 - Insecure TLS Custom Verification Gap
**Vulnerability:** When using `InsecureSkipVerify: true` with a custom `VerifyPeerCertificate` callback in Go, the TLS implementation does not automatically verify certificate expiration dates (`NotBefore` and `NotAfter`). The codebase was only verifying the certificate's SHA-256 fingerprint, allowing expired certificates to be accepted.
**Learning:** `InsecureSkipVerify: true` completely disables all default validation, including timestamp checks. `VerifyPeerCertificate` is limited because it lacks connection context and explicit expiration verification.
**Prevention:** In Go 1.15+, always use the `VerifyConnection` callback instead of `VerifyPeerCertificate` when custom validation is required. This allows explicit manual validation of the certificate's expiration window (`NotBefore`/`NotAfter`) alongside custom checks like fingerprint pinning.

## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.

## 2024-06-25 - TLS Certificate Expiration Validation Bypass
**Vulnerability:** The P2P transport layer (`internal/netp2p/tls_transport.go`) used `VerifyPeerCertificate` to validate a custom self-signed certificate via its SHA-256 fingerprint. However, it failed to validate the certificate's validity dates (`NotBefore` and `NotAfter`).
**Learning:** Using `InsecureSkipVerify: true` with a custom `VerifyPeerCertificate` overrides the default Go TLS validation logic, meaning expiration checks are skipped unless explicitly implemented. This could allow an attacker to reuse a captured, valid-but-expired certificate indefinitely, bypassing the intended 72-hour ephemeral credential limit for P2P connections.
**Prevention:** When implementing custom TLS certificate pinning or validation (e.g., using `InsecureSkipVerify`), use `VerifyConnection` (preferred in Go 1.15+) instead of `VerifyPeerCertificate`. Always explicitly validate the certificate expiration against the current time (`time.Now()`) to ensure the certificate is within its valid date range.

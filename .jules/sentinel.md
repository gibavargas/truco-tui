## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2026-05-21 - Fix P2P TLS fingerprint verification to validate expiration and use constant-time comparison
**Vulnerability:** The custom TLS `InsecureSkipVerify` logic only verified a SHA-256 fingerprint using a string equality check, leaving it vulnerable to timing attacks and accepting expired certificates.
**Learning:** When writing custom TLS `VerifyPeerCertificate` (or `VerifyConnection`) logic, Go bypasses all built-in certificate checks. You are fully responsible for checking validity windows (`NotBefore`, `NotAfter`), hostnames (if applicable), and using constant-time algorithms for sensitive hash comparisons.
**Prevention:** Use `tls.VerifyConnection` to easily access parsed `PeerCertificates`. Always include `time.Now().Before(cert.NotBefore) || time.Now().After(cert.NotAfter)` checks. Always use `crypto/subtle.ConstantTimeCompare` instead of `==` for cryptographic material comparisons.

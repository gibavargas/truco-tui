## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.
## 2026-05-15 - Explicit Certificate Verification
**Vulnerability:** The code relied on `InsecureSkipVerify: true` and `VerifyPeerCertificate` to pin TLS certificates, but `VerifyPeerCertificate` only provides the raw certificate bytes, requiring manual extraction and parsing for expiration and structure checks.
**Learning:** In Go, `VerifyConnection` is generally preferred over `VerifyPeerCertificate` for custom verification logic when `InsecureSkipVerify: true` because it provides pre-parsed `x509.Certificate` structures (in `tls.ConnectionState.PeerCertificates`), allowing simple validation of properties like expiration (`NotBefore`/`NotAfter`) without needing to duplicate the certificate parsing logic.
**Prevention:** Use `VerifyConnection` when overriding standard verification with `InsecureSkipVerify: true` to perform robust, explicit checks on parsed certificate states rather than solely relying on fingerprinting raw bytes.

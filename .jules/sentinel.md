## 2024-04-14 - Predictable Fallbacks in Cryptographic Entropy Sources
**Vulnerability:** Several functions (`newRelayServer` and `randomHex` in `cmd/truco-relay/main.go`, and `randomKey` in `browser-edition/cmd/httpapi/main.go`) used predictable fallback values (hardcoded strings or timestamps) if `crypto/rand` failed to generate entropy.
**Learning:** Falling back to predictable values when entropy generation fails compromises the security of cryptographic operations, session keys, and secrets. It creates a silent failure where the system appears to work but is fundamentally insecure.
**Prevention:** If an entropy source fails during cryptographic operations or secret generation, the application must panic and fail-closed rather than continuing with insecure fallback values.

## 2024-05-24 - Cryptographic Entropy and Map Secrets
**Vulnerability:** Found `rand.Read` ignoring severe entropy failures (returning errors that might be swallowed) and sensitive `replaceToken` authentication strings stored in plaintext within a long-lived Go map (`h.replaceInvites`).
**Learning:** Returning errors from fundamental OS entropy failure functions (like `rand.Read` generating 16 bytes for tokens) is dangerous because callers might not handle the error correctly or might log it and proceed with zeroed/predictable tokens. Also, long-lived server maps storing plaintext tokens create significant risk vectors for defense-in-depth, as map memory is often targeted by exploits or inadvertently dumped in logs.
**Prevention:** Always panic (`panic("entropy source failed")`) when generating secure random tokens if the OS cannot provide entropy; the system is fundamentally broken and must fail-closed. When maps must associate secrets with internal state (like mapping replacement tokens to seats), hash the tokens first using `sha256` and use the hash as the map key. Ensure `subtle.ConstantTimeCompare` is used anywhere tokens are compared.
